# Research Ledger — โครงสร้างบัญชีอ้างอิงงานวิจัย

เอกสารนี้กำหนดวิธีเก็บผลการค้นคว้าจาก skill นี้ให้เป็น **บัญชีอ้างอิงถาวรของ repo** ที่ตอบสองโจทย์พร้อมกัน: (1) เป็นหลักฐานงานวิจัยรองรับการตัดสินใจเชิงสถาปัตยกรรม/ดีไซน์ (2) หยิบ citation ไปแปะบนหน้าเว็บ/แอปได้ทันที

## หลักการออกแบบ

- **Markdown คือ source of truth เดียว** — เหตุผลเดียวกับ CONTEXT.md/design.md: agent อ่านได้ดีที่สุด, diff/merge กับ git ได้, มนุษย์แก้ได้ ห้ามดูแลสองแหล่งขนานกัน
- **Excel/CSV เป็นผลลัพธ์ที่ derive ได้** — ถ้าต้องการดูใน Excel ให้ generate CSV จาก ledger ตอนขอ (สูตรด้านล่าง) แล้วทิ้งหลังใช้ อย่าเก็บเป็นไฟล์ถาวรคู่กัน เพราะจะ sync ไม่ทัน
- **ไฟล์ละหัวข้อ** — ไฟล์ไม่บวม เลื่อนอ่านง่าย และหยิบทั้งไฟล์ไปใช้ที่อื่น (เช่น แปะเนื้อหามุม research บนเว็บ) ได้ทั้งก้อน
- **Lazy creation** — ไม่ต้องสร้าง `research/` ล่วงหน้า สร้างเมื่อ skill บันทึกครั้งแรก

## โครงสร้างไฟล์

```
research/
├── README.md                 ← ดัชนี: หัวข้อไหนบ้าง อัปเดตเมื่อไหร่
└── <topic-slug>.md           ← ไฟล์ละ 1 หัวข้อ/การตัดสินใจ
```

ตั้งชื่อไฟล์เป็น slug ภาษาอังกฤษพุ่งล่าง เช่น `streaming-vs-polling.md`, `thai-tokenization.md`

## Schema ของไฟล์หัวข้อ (คัดลอกโครงนี้ทุกครั้ง)

```markdown

> **สถานะ:** current
> **อัปเดตล่าสุด:** YYYY-MM-DD (วันที่รันการค้นคว้าล่าสุด — ใช้เป็น anchor ของความสด)

- **ทำไมสำคัญกับการตัดสินใจนี้:** <กลไกทางเทคนิค 1 บรรทัด>
- **Cite blurb (พร้อมแปะเว็บ):** "<อธิบาย 1-2 ประโยคภาษาผู้อ่านเว็บ + ลิงก์ ให้คนทั่วไปคลิกอ่านต่อได้>"

### 2. [ชื่อเปเปอร์](ลิงก์)
(โครงเดียวกัน)

### 3. [ชื่อเปเปอร์](ลิงก์)
(โครงเดียวกัน)

## งานอื่นที่ทิศทางเดียวกัน (เกิน 3 อันดับแรก)
```

## กฎของห่วงโซ่หลักฐาน (Evidence Chain)

1. **เรียงใหม่สุดก่อนเสมอ** — anchor คือวันที่ทำการค้นคว้า (เช่น 2026-09-09) ปรับลำดับใหม่ทุกครั้งที่แทรกงานที่ใหม่กว่าเข้ามา
2. **สูงสุด 3 รายการในห่วงโซ่** — เลือก 3 ตัวที่มีน้ำหนักข้อเสนอ/คัดค้านการตัดสินใจนี้มากที่สุดโดยเริ่มจากใหม่สุด ส่วนที่เหลือลงหมวด "งานอื่นที่ทิศทางเดียวกัน" เป็น bullet บรรทัดเดียว เพื่อสื่อว่ามีหลายงานวิ่งไปทางเดียวกันโดยไม่ทำให้หน้าแรกรก
3. **ทุกรายการต้องระบุ relation ต่องานอื่น** — ไม่มี paper ไหนลอยอยู่คนเดียว ถ้าเป็นงานแรกของหัวข้อจริง ๆ ให้เขียน `รากของหัวข้อนี้` (root)
4. **ห้ามลิงก์กุ** — ทุกลิงก์ต้องเป็น `https://arxiv.org/abs/...` ที่เปิดได้จริง ตาม guardrail "No Hallucinated Citations" ของ skill
5. **supersede แทนการลบ** — ถ้างานใหม่หักล้างงานเก่าจนการตัดสินใจเปลี่ยน ให้แก้ "การตัดสินใจที่งานวิจัยรองรับ" ใหม่ เปลี่ยนสถานะหัวข้อเก่าที่ตายแล้วเป็น `superseded by <slug>` แล้วสร้างไฟล์ใหม่ให้การตัดสินใจปัจจุบัน

## Relation Taxonomy

| ค่า | ความหมาย | ใช้เมื่อ |
| --- | --- | --- |
| `supports` | งานใหม่เกื้อหนุนข้อสรุปเดิม | ผลทดลองเดินทางเดียวกับงานเก่า |
| `refutes` | งานใหม่หักล้างข้อสรุปเดิม | เปเปอร์แบบ "rethinking/revisiting/does not" พิสูจน์ว่าของเดิมใช้ไม่ได้ |
| `extends` | งานใหม่ต่อยอดงานเก่า | ขยายขอบเขต/เพิ่มความสามารถบนฐานเดิม |
| `bounded-by` | งานใหม่จำกัดเงื่อนไขของงานเก่า | ของเดิมยังใช้ได้ แต่เฉพาะเงื่อนไขที่งานใหม่ชี้ |

รูปแบบการเขียน: `refutes → [ชื่องานเก่า](ลิงก์) (ปี)` — หนึ่งรายการอ้างงานเก่าได้หลายฉบับโดยคั่นด้วย `;`

## กฎของ Cite Blurb (ของที่แปะเว็บ)

- ภาษาเดียวกับผู้อ่านเว็บ (ถ้าเว็บเป็นภาษาไทย เขียนไทย คงศัพท์เทคนิคอังกฤษไว้ตามกติกาของ skill)
- 1-2 ประโยค: ประโยคแรกบอกว่ากลไก/ข้อค้นพบคืออะไร ประโยคที่สองบอกว่ามันเปลี่ยนอะไร — ใช้อุปมาชีวิตประจำวันตามลีลาของ skill
- ปิดท้ายด้วยลิงก์ `https://arxiv.org/abs/...` เสมอ เพื่อให้คนคลิกอ่านต้นทางได้
- เขียนให้ "ยืนเดี่ยวได้" — คนที่ไม่ได้อ่าน ledger ทั้งไฟล์ต้องเข้าใจได้จาก blurb เดียว

## Export เป็น Excel/CSV (derive เมื่อขอ)

สร้าง `research-export.csv` ชั่วคราวจากทุกไฟล์หัวข้อ ด้วยคอลัมน์:

```
topic_file, decision, paper_title, arxiv_id, url, published, relation_type, relation_to_url, why_it_matters, cite_blurb, recorded_on
```

บอกผู้ใช้เสมอว่าไฟล์นี้ snapshot ณ วันที่ generate และ **ไม่ใช่** source of truth

## README.md (ดัชนี)

```markdown
# Research Ledger — ดัชนี

บัญชีอ้างอิงงานวิจัยที่รองรับการตัดสินใจเชิงสถาปัตยกรรมของ repo นี้
จัดการผ่าน skill `arxiv-deep-researcher` · อัปเดตล่าสุด: YYYY-MM-DD

| หัวข้อ | ไฟล์ | สถานะ | อัปเดต |
| --- | --- | --- | --- |
| <ชื่อหัวข้อ> | [slug.md](slug.md) | current | YYYY-MM-DD |
```

เพิ่ม/แก้แถวในดัชนีทุกครั้งที่สร้างหรือแก้ไฟล์หัวข้อ สถานะใช้ `current` / `superseded`
