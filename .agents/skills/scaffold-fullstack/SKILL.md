# Scaffold Fullstack

Create the repo layout so each language's tooling owns its own directory and nothing fights. The design principle: uv and bun/pnpm never integrate — they coexist by separation.

## Workflow

1. **Confirm the stack before creating anything.** Ask (or infer from an existing decision in `CONTEXT.md`/ADRs): backend framework (default FastAPI), frontend framework (default Next.js; Vite for lighter apps), package manager for TS (default bun; pnpm when the user prefers it), Python version (`requires-python`), and whether a devcontainer is wanted. Do not scaffold on guesses for framework choice — everything else defaults silently.
2. **Create the separated layout.**

   ```
   <repo>/
   ├─ backend/            # Python — uv's world
   │  ├─ pyproject.toml   # project + deps + requires-python
   │  ├─ uv.lock          # generated by `uv lock`
   │  └─ (app/ source)
   ├─ frontend/           # TypeScript — bun/pnpm's world
   │  ├─ package.json
   │  ├─ <lock file>
   │  └─ (source)
   ├─ .gitignore          # both .venv/ and node_modules/ ignored
   ├─ justfile            # orchestration
   └─ README.md           # boot instructions in ≤5 commands
   ```

   Never place `package.json` and `pyproject.toml` in the same directory — each tool scans up for its own manifest.

3. **Set up the Python side with uv.** `uv init backend` (or hand-write `pyproject.toml`) → add deps with `uv add fastapi uvicorn` → confirm `uv.lock` + `backend/.venv` exist → smoke: `uv run uvicorn app.main:app` (or the framework's run command) serves a health route. `uv run` is the only documented way to execute Python here — no activate-venv steps in the README.
4. **Set up the TypeScript side.** `bun create next frontend` (or the chosen framework) → `bun install` → smoke: dev server boots. Frontend calls the backend through its dev proxy (`vite.config.ts` proxy or `next.config.js` rewrites) pointing at the backend port — never CORS-workaround during dev.
5. **Write root orchestration.** A `justfile` with `dev` (both servers, parallel), `install` (uv sync + bun install), `check` (ruff + tsc, extend later), and `clean` (both ecosystems). Each recipe `cd`s into its stack directory and delegates to that stack's tool — the justfile itself is language-agnostic.
6. **Write environment configs.** `.gitignore`: `.venv/`, `node_modules/`, `.env*`, `__pycache__/`, `dist/`, `__ruff_cache__`, `.next/`. VS Code: `.vscode/settings.json` with `python.defaultInterpreterPath` pointing at `backend/.venv` (Windows: `backend/.venv/Scripts/python.exe`) so the Python language server binds the venv without touching the TS server. Devcontainer (if requested): one image per stack, not one merged image.
7. **Prove the boot.** Run `just install` then `just dev` fresh (or the README's exact commands in order) — the scaffold is not done until both servers respond and the frontend proxy reaches the backend health route. Report the layout, the ≤5-command boot path, and which commands were verified.

## Guardrails

- Lock files are committed; `.venv/` and `node_modules/` are not — regeneration always comes from the lock.
- Pin `requires-python` in `pyproject.toml`; uv downloads the interpreter — do not rely on the system Python version.
- If the user only needs Python (no frontend), this skill still applies minus step 4–5's frontend recipes; if the user only needs TS, it is not this skill.
- Pair with `/api-contract` once both sides exist and you start defining endpoints — the scaffold provides the directories, the contract skill provides the seam.
- Pair with `/design-md` on the first UI-bearing run after scaffolding, per the workspace flow.
